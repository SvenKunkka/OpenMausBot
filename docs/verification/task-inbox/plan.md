# Sven Bots 任务收件箱功能规划

2026-11-10 · 面向本机 Sven Bots 单人使用

## 目标

用户在同一个机器人聊天里连续发出两件事，可以独立追踪每件事从接单到结果的状态。第一件完成后，即使用户已切到其他聊天或关过应用，也能从收件箱打开对应结果。

本期覆盖本机桌面的一对一聊天，以 Codex 作为首条验收链路。同一聊天按顺序执行独立任务，复用当前会话上下文。同一工作区中不同聊天的任务共同出现在收件箱，由现有并发规则决定何时运行。

## 现状依据

- 本机安装版本为 0.1.151-workbench.5。源码在 [OpenMausBot](../../..)。核对时，本地 main、origin/main 引用和版本标签指向同一提交 25b4cdf，工作区干净。安装产物与该源码目录的本地发行产物已比对。
- 本机收件箱收录审批、提问、机器人主动消息、例行任务结果和部分异常。普通聊天回复完成时不会自动增加结果条目。现有活动区域按聊天展示，无法区分同一聊天中的两个任务。见 [收件箱入项规则](../../../server/host/place-inbox.ts#L211) 和 [活动列表](../../../src/components/inbox/InboxActive.tsx#L14)。
- 当前客户端忙时发送的默认配置允许把新消息补进正在执行的轮次。已排队的短时间连续消息也可能合并。现有结束提醒在后面有任务排队时可能被抑制。这三处都会影响逐任务追踪。见 [发送模式](../../../shared/follow-up.ts#L9)、[队列合并](../../../server/steer-queue.ts#L197) 和 [结束提醒](../../../server/done-notice.ts#L19)。

## 用户体验

| 场景 | 用户看到什么 |
| --- | --- |
| 发出新任务 | 服务端确认接单后，显示简短回执。任务立即出现在「进行中」，标明执行中或排队中。 |
| 旧任务未结束时再按发送 | 默认「排队为新任务」。新消息有独立条目，旧任务继续。要给旧任务补材料时，通过发送菜单选「补充当前任务」；审批和提问走现有卡片。 |
| 切到其他聊天 | 左侧收件箱入口可直接打开。每行显示任务标题、机器人、状态、最近一次实际进展及时间。排队条目可定位原聊天，等待确认的条目可定位对应卡片。 |
| A 回复时 B 已开始 | A 同时出现在「结果未看」，B 留在「进行中」。点击 A 定位到它自己的回复。 |
| 任务失败、停止或重启中断 | 条目显示对应原因和已有结果。用户可以查到状态，并决定是否另发任务。 |
| 看完结果 | 打开并实际显示对应结果，或手动标为已看。未看计数随之变化，记录仍可从任务列表的「全部」筛选找回。 |

左侧继续使用「收件箱」入口。面板内分「进行中」「结果未看」「消息与审批」三栏，任务区域提供「全部」筛选。进入收件箱时有未看结果就优先显示该栏，否则显示进行中。已有审批标识与任务未看计数各自对应自己的条目。结果准备好时用应用内条目和计数提示，系统通知沿用现行规则。

桌面使用现有侧板，窄屏使用现有底部面板。沿用 Sven Bots 的蓝灰色、字号和列表间距。标题、状态文字、结果入口优先显示，时间和最近进展使用次级字重。状态同时提供文字，键盘可浏览和打开条目。

## 状态口径

| 状态 | 写入依据 |
| --- | --- |
| 排队中 | 服务端已持久保存请求，尚未领取执行。可显示「等上一任务」「等你处理上一任务」或「等执行名额」。 |
| 执行中 | 执行器实际开始，绑定本次执行 ID。进展来自可展示的执行事件，带真实时间。 |
| 等待协作 | 主任务已挂起，协调器仍在等待需要回报的子任务。 |
| 等你处理 | 原任务实际挂起，等待提问、批准或登录。继续执行沿用同一个任务 ID。 |
| 已回复 | 能确认最终回复归属，执行已正常收尾，相关等待和需要回报的委派已结算。回复可包含局部成果或数据缺口。 |
| 失败、已停止或已中断 | 取执行失败、明确停止、重启或运行失联的证据。保存能查到的部分结果和简短原因。 |

执行状态与结果是否已看分别保存。成功生成回复表示机器人已交付一条结果，外部操作是否完成由该操作的回执决定。截图里的「写推文」和「设定定时」如果有可验证的进展，可以作为两条进展显示。定时是否建成以实际设置回执为准。

## 实现决策

1. **沿用现有发送与执行链。** 为本机一对一普通发送增加明确的独立任务语义，覆盖可补充和不可补充的引擎。独立任务不被短时间连续发送合并，也不因用户消息优先而抢占上一任务。「补充当前任务」沿用现有定向发送，在支持的引擎上启用。若目标轮已结束或补充投递结果不明确，界面提示当前状态，避免自动重放。
2. **在消息库里持久保存任务。** 复用 SQLite 的现有聊天队列，增量记录任务 ID、工作区、机器人、会话、发送 ID、队列 ID、原消息、执行和结果引用、最近进展、结束原因及查看时间。同一发送重试使用同一个发送 ID。服务端保存后才确认接单，任务记录与队列的创建及领取保持一致。聊天正文仍由消息库管理。
3. **从真实事件归集状态。** 使用现有请求归属、执行启动、等待、停止和结算信息。旧轮结果在开启下一轮前落账。启动恢复时，未领取的队列照既有规则继续，已领取且不能确认结算的任务标为已中断；已能证明收尾的恢复为结果。需要同时对齐聊天队列和协调器的启动恢复规则，确保同一任务只有一处负责派发。见 [协调器恢复](../../../server/runtime/runtime.ts#L79)。
4. **收件箱按任务跳转。** 用结果消息 ID 定位，支持加载历史页和断线重新同步。结果出现在当前窗口的可见区域后才清该任务的未看标记。失败或中断条目可直接打开原因详情。对仍有权限的任务，结果定位失败时提示原因并保留未看，用户仍可手动标为已看。列表、推送和读取状态写入都按工作区和会话权限过滤。会话删除时清理对应任务记录。

现有落点包括 [消息队列表](../../../server/message-db.ts#L69)、[忙时接单判定](../../../server/admission.ts#L100)、[请求结算条件](../../../server/index.ts#L4588)、[重启恢复](../../../server/index.ts#L15436) 和 [收件箱面板](../../../src/components/inbox/InboxPanel.tsx#L111)。上线后的新任务开始入账，已有聊天仍按历史消息查看。

## 施工顺序与发布条件

1. 在隔离环境复现连发两条任务，固定发送、补充和恢复的基线。
2. 打通「接单 → 运行 → 回复归档」链路，验证 A、B 的归属与重复发送。
3. 接上收件箱，打通等待处理、未看计数和精确定位。
4. 验证重启、停止、失败和跨页结果，完成桌面和手机宽度的截图检查。
5. 构建本地候选包。在隔离数据上演练升级与回退，通过后再进入正式替换环节。

源码规则要求使用隔离测试环境。使用项目自带的假引擎和临时数据目录，指向夹具分配的端口。历史日志记录了全量测试的 73 个失败项，开工须复跑并登记基线。放行要求为改造链路全部通过、全量测试无新增失败、构建通过并完成界面核验。正式更新前按本机备份规则验证原应用与受影响工作区的完整可恢复性，按一致性方式处理 SQLite 数据及相关配置，并演练回退。 [项目验证规则](../../../docs/verification/README.md#L9)

逐项依赖、验收和检查点见 [施工清单](todo.md)。
